**Mandrake purple flower smear (reopened+re-fixed 2026-06-11; original 2026-06-10 diagnosis was wrong):**
- The Mandrake crop's purple flowers smear/halo on screen at distance. **The 2026-06-10 "fix" did not work** — it was based on a wrong model of MC's mipmap blend. Verified against `net.minecraft.client.renderer.texture.MipmapGenerator`: when a texture has any transparent pixel, the mip blend (`alphaBlend`, transparent branch) sums each texel's colour **only `if (col >> 24 != 0)`** — i.e. **fully-transparent (alpha 0) pixels are skipped; their RGB is ignored.** So the original "alpha-bleed 44 crop textures" pass (recolouring alpha-0 transparent pixels, alpha preserved) was a **no-op** for this smear — those pixels don't contribute to the blend at all. (Harmless, left in place.)
- **Real cause:** the **opaque purple flower itself** (alpha-255 pixels — 27 in stage 4, 6 in stage 3) bleeds its colour into adjacent texels via mipmaps. Mandrake's alpha histogram is just `{0, 1, 255}`; only 2 low-alpha pixels exist, so the smear is the flower, not stray transparent pixels. Alpha-bleeding can never touch this (it only recolours transparent pixels; the flower is opaque). The only real lever (short of disabling mipmaps, which isn't per-texture controllable) is the flower's own colour intensity.
- **Real fix (2026-06-11):** muted the flower's purple in `mandrake_stage_{2,3,4}.png` (HSV saturation ×0.72, value ×0.85) so its mip-halo is gentler; zeroed the 2 stray alpha-1 pixels per texture. Green leaves/stem untouched. Trade-off: less smear vs a less-neon flower; dialable via the sat/value factors. Belladonna's purple flowers share the inherent issue (not yet muted). In-game QA pending. Mechanism write-up: [FX_TECHNIQUES](../reference/FX_TECHNIQUES.md) (Glamour Bleed — the same physics used on purpose).

**Closed 2026-06-10 (Wolfsbane crop render QA):**
- ~~Wolfsbane crop renders as a flat "green cross" with missing-looking art~~ — not a texture or mapping problem (the 8 `wolfsbane_stage_*.png` are the authentic 1.7.10 art and the blockstate/age wiring is correct). Audited every cross-crop model afterward — wolfsbane was the only one missing the render type / carrying a BOM. Block-resource only; in-game QA to confirm.

Build + 134 tests green; `runData` regenerated the Primer JSON.

### 4. Morsmordre glyph cannot be drawn — symbol recognition (in-game QA 2026-06-03) — FIXED 2026-06-03

Root cause was a transcription bug, not the recogniser. The source `StrokeSet` has two constructors —
`(int level, byte... strokes)` and `(byte... strokes)`; Morsmordre used the no-level one, so
`new StrokeSet(0, 0, 3, 2, 2)` is the full sequence `[0,0,3,2,2]`. Copied verbatim into the port
(whose `StrokeSet` is always level-first), the leading `0` became **level 0** and the strokes became
`[0,3,2,2]` — so drawing up-up-… landed on Expelliarmus's `[0,0,1]`. Fixed by prepending the level
(`new StrokeSet(1, 0,0,3,2,2)` …) so Morsmordre is level 1 with the correct glyph **up, up, left,
right, right**. Verified via script that no spell's stroke sequence is a prefix/duplicate of another
across the whole roster (41 sets), so the freeze-on-first-match recogniser is safe as-is.
File: `symbol/EffectRegistry.java`.
- **Follow-up (2026-06-03):** glyphs still wouldn't chain — "up then down" cast Expelliarmus. The
  stroke detector (faithful to source `ItemMysticBranch.onUsingTick`) appended a stroke *every tick*
  the cumulative move exceeded 7°, so one fast up-flick became `[0,0]`, then a down gave `[0,0,1]` =
  Expelliarmus. Reworked `client/SymbolDrawState` to debounce: after a stroke it waits for the look
  to settle (per-tick move < 2.5°) before arming the next, so **one flick = one stroke** and multi-
  stroke glyphs chain (flick, pause briefly, flick…).
