# Active Bugs

Last reconciled: 2026-05-31. Latest village structure/wall bugs are closed; see `docs/archive/BUGS_CLOSED.md` for the older history.

**Closed 2026-05-31:**
- ~~/witchery goto marks villages walled after zero gate candidates and can land underground~~ - the 19:38-19:44 log showed natural discovered villages generating good walls, while goto-prep full-chunk loading immediately ran the generator with `0 gate candidate(s)`, marked those villages processed, teleported, and made `/witchery walls` refuse until `walls reset`; the same villages then produced normal gate candidates through the command path. Fixed: wall generation now reports whether it actually placed walls, `0 gate candidate(s)` skips placement and leaves the village unprocessed, goto-prep/manual wall jobs retry briefly while road chunks settle, and village goto selects a safe loaded road/surface landing instead of the raw locate X/Z.
- ~~Village wall freeze logs lack enough breadcrumbs~~ - hard freezes often left the last useful line several operations before the actual stall point. Fixed: `config/witchery-common.toml` now has top-level `debug = true` by default, and the village wall/goto paths log `[VillageWalls:Debug]` breadcrumbs around queue state, loaded-only references, safe locate probes, chunk prep, forced tickets, footprint readiness, and generator entry. Set `debug = false` once the wall queue is stable to quiet the extra diagnostics.
- ~~Fresh-world exploration can freeze after several automatic village wall queues~~ - the 19:17 log stopped after two passive village starts queued near spawn and both logged natural wall-chunk waits, with no Java exception. The automatic wall job itself no longer force-loaded wall chunks, but the passive structure-reference fallback still synchronously loaded referenced village start chunks and the active wall queue could be head-of-line only when several villages arrived together. Fixed: automatic village start lookup/refresh now uses `getChunkNow` only, safe village goto passes its located `StructureStart` into arrival prep directly, active wall jobs rotate through a bounded two-step budget, and pending automatic starts scan/check only a bounded set per tick while queueing at most one ready generation job.
- ~~/witchery goto can teleport into ungenerated void and freeze after safe locate~~ - the 19:07 taiga/snowy log found a village 5344 blocks away, prepared one chunk, teleported, then stopped at `Waiting for naturally loaded wall chunks ... 1/168 ready` while the player was already in empty terrain. Fixed: village goto now queues a pre-teleport arrival prep job that full-loads the target village footprint one chunk per tick, generates walls/gates before crossing for unprocessed villages, and prepares a smaller 5x5 landing bubble before crossing to already processed villages.
- ~~Village walls and gate paths leave half-cut taiga trees~~ - wall columns and graded gate paths could overwrite or clear only the exact blocks in their corridor, leaving sliced spruce trunks or floating canopies beside the new path. Fixed: wall columns, gatehouses, and graded gate paths now detect touched `LOGS`/`LEAVES` and clear the connected natural tree material within a bounded local radius while preserving village wood blocks like planks and fences.
- ~~Bookshop roof floats / bookshop sits too high / village panes do not connect~~ - the first live Bookshop used a newer full-box gable that did not match old `ComponentVillageBookShop`, sat one block too high from village paths, and used default glass-pane states. Fixed: Bookshop now uses the old compact footprint and stair roof with a lowered path-height baseline, and Bookshop/Witch Hut panes are emitted with explicit wall-connection states.
- ~~One village can generate several copies of the same Witchery building~~ - after the house-pool weight increase, fresh QA found four village Witch Huts in one village. Fixed: `WitcheryVillageElement` now keeps a per-village claim set keyed by the owning village `StructureStart` when available, and skips duplicate apothecary, bookshop, witch hut, watch tower, or keep placements in that village while allowing repeated chunk passes for the same selected piece.
- ~~/witchery goto can freeze before teleporting to the second found village~~ - the 15:48 taiga log found the village and queued `132 wall chunk ticket(s)`, then stopped before even logging the first `Requested 10/...` progress line. The freeze point was the first forced wall-chunk ticket, not locate, wall generation, or teleport. Fixed first by removing forced wall pre-generation from village goto; the later 19:07 void-arrival fix supersedes the one-chunk immediate teleport path with pre-teleport chunk prep and wall generation.
- ~~/witchery goto village_savanna can stall on the fourth chained village goto~~ - the 14:32 savanna log stopped while the wall pre-generation job was waiting on `15/16 requested ready`, before `VillageWallGenerator.generate` ran or the player teleported. Fixed: explicit goto/walls jobs now sort forced wall chunks nearest-first, cap very large forced footprints at 144 chunks, request one chunk ticket at a time, and release/skip a forced chunk that makes no readiness progress for 10 seconds instead of holding the whole job. Gate terrain adaptation was also bounded so inward gate path height fixing and height sampling stop at 10 blocks and no longer flatten paths deep into houses.
- ~~/witchery goto village_plains can freeze after "Requested all wall chunk tickets"~~ - the 13:39 plains log showed locate and start resolution completing, then the wall job queued all 195 padded-footprint forced chunk tickets within one burst and stopped before readiness/generation logs. Fixed: explicit goto/walls jobs now request one chunk ticket at a time and wait for the requested chunk to be present in `getChunkNow` before issuing the next ticket; timeout tracking is progress-based so a stuck batch is released/skipped instead of flooding worldgen.
- ~~Witchery village buildings never appear in vanilla villages~~ - the procedural `WitcheryVillageElement` had no connectable jigsaw block, so village house pools could list Witchery buildings without ever attaching them to streets. Fixed: the element now exposes a north-facing `minecraft:building_entrance` connection for the generated piece, allowing apothecaries, bookshops, witch huts, watch towers, and keeps to be selected by village pools.
- ~~Village wall generation freezes when `/witchery goto` is chained~~ - wall setup was force-loading every chunk in the village bounding box plus padding in one server tick. Fixed: wall jobs now use temporary forced-chunk tickets instead of synchronous chunk generation, and `/witchery goto` has a per-player cooldown.
- ~~Village walls/gates still fail on water and hill edges~~ - the RC wall pass now avoids placing walls under water, keeps walls at water level when crossing water, centers gatehouses on the wall line, grades approaches to hilly gates, prefers biome-appropriate road/path materials, and keeps corners from overwriting gates.
- ~~Village wall gates can attach sideways to a nearby path~~ - gate detection accepted any road ray that reached a wall cell, even if the road clipped the side of a wall segment/corner. Fixed: gate candidates now require the road to hit a three-wide flat wall face head-on, with interior behind the approach and empty/outside space beyond the wall.
- ~~Straw Man can generate below water~~ - the first pass only checked center/corner water and allowed all overworld biomes, so water inside the 6x5 footprint or river/ocean terrain could slip through; a later report showed the structure-selection heightmap guard could still be fooled by actual water at placement time. Fixed: generation rejects any wet footprint column and ocean/river biomes before adding the piece, and `StrawManPiece.postProcess` now aborts before writing blocks if the live 6x5 footprint has water by fluid or heightmap state.
- ~~Straw Man badlands base uses a raised pale sand platform~~ - the port treated badlands like deserts for the ground material and flattened/fill-supported the whole 6x5 footprint from the center column. Fixed: Straw Man placement now rejects overly uneven footprints, anchors at the lower accepted footprint height, keeps forced sand to actual deserts, samples local solid surface blocks for non-desert ground/support, and fills support only under the cross footprint.
- ~~Automatic village walls can be missed around `/witchery goto` targets~~ - the queue could rely on a chunk-load event from the wrong village chunk or mark an early empty start as processed, while `/witchery goto` only teleported and hoped the queue fired. Fixed: queued starts refresh/retry until ready, non-start village chunks can queue via structure references, and village goto now queues wall pre-generation before teleport.
- ~~Village wall pre-generation can freeze the integrated server~~ - the 11:13 plains log showed wall generation finishing but only after one tick synchronously force-loaded 56 perimeter chunks, producing a 4.59s server catch-up warning and a later client shutdown watchdog. Fixed: `/witchery goto village_*` and `/witchery walls` now queue temporary forced-chunk wall jobs, wait for needed wall chunks to load over normal ticks, generate walls, release tickets, and only then complete pending village teleports.
- ~~Automatic village walls can generate with zero gate candidates~~ - the 11:31 logs showed several automatic villages reaching `0 gate candidate(s)` because the queued job waited only for perimeter chunks while gate detection scans existing village roads inside the wall footprint. Fixed: automatic wall jobs now wait for the padded village footprint to be naturally loaded before `VillageWallGenerator.generate`, while explicit goto/walls jobs pre-load nearby wall-footprint chunks through readiness-gated temporary tickets before selecting gates.
- ~~`/witchery goto village_*` can duplicate walls or freeze after a large wall-ticket request~~ - the 12:32-12:35 logs showed an already processed plains village at the same bounding box being force-generated a second time, then a savanna goto stopping right after a 210-ticket padded-footprint request. Fixed: village goto and the normal `/witchery walls` command now respect the processed-village set unless `/witchery walls reset` is used first, and explicit wall jobs request nearest-first forced-chunk tickets one at a time before generating walls/gates.
- ~~Automatic wall jobs can freeze fresh world entry~~ - the 12:48 fresh-world log showed an automatic spawn-village queue starting a 210-ticket padded-footprint request while the integrated server had only generated a few spawn chunks. Fixed: automatic chunk-load discovery now waits for the full padded wall footprint to become naturally loaded by normal view-distance/player chunk loading, and only command/goto wall jobs request forced chunk tickets.
- ~~Chained vanilla village goto can freeze during locate before any wall job starts~~ - the 12:57-13:00 run completed automatic walls plus savanna/snowy gotos, then froze after `[Goto] Searching for minecraft:village_plains...]` and before `[Goto] Prepared...`, isolating the stall to vanilla `findNearestMapStructure` scanning too far for a biome-specific village. Fixed: vanilla village gotos now use radius 8 instead of the general radius 32, and stale automatic pending wall entries skip once the same village is already processed.
- ~~Chained vanilla village goto can still freeze inside bounded locate~~ - the 15:02 run completed one natural village plus several gotos with walls, then froze after `[Goto] Searching for minecraft:village_plains ...]` with no later destination prep or wall logs. Fixed: village gotos no longer call vanilla `findNearestMapStructure` synchronously. They now queue a safe locate job that probes one candidate village chunk per server tick; the later 19:07 follow-up adds pre-teleport chunk prep and wall generation before crossing. Manual `/witchery walls` also avoids vanilla locate and only queues walls for a nearby generated village start.

## Open

### 1. Village goto pre-teleport prep needs follow-up retest

The 2026-05-31 village fixes now cover thirteen observed stall/false-success paths: ticked safe village locate instead of synchronous vanilla locate, pre-teleport one-chunk-per-tick arrival prep, no forced wall tickets before village goto teleport, walls/gates generated before crossing to unprocessed goto villages, nearest-first one-chunk forced-ticket batches for manual wall jobs, a 144-chunk cap for very large explicit forced footprints, no forced wall tickets for automatic world-entry discovery, loaded-only automatic village reference lookup/refresh, bounded multi-village queue rotation/checking, stuck forced-chunk release/skip after 10 seconds without readiness progress, stale processed-village duplicate skips, the 19:07 one-chunk void arrival freeze, and the 19:38-19:44 `0 gate candidate(s)` false processed state. Retest on fresh plains/savanna/desert/taiga/snowy villages after restarting the client, with special attention to automatic spawn villages logging natural chunk waits instead of forced tickets or hidden start-chunk loads, village gotos logging `Queueing safe village search`, `Safe village locate found`, `Queued village arrival prep`, `Preparing village arrival`, wall generation before teleport for fresh villages, and the teleport chat only after prep completes. Explicit `/witchery walls` jobs should still log one-chunk requested-batch waits instead of a large "requested all" spike; manual `/witchery walls` should fail cleanly when no generated village start is nearby; biome-specific village gotos should fail cleanly if the safe radius has no match; and villages should show no duplicate wall layers, no completed generation after `0 gate candidate(s)`, nonzero gate candidates on ordinary road villages, road/safe-surface goto landings instead of underground arrivals, and gate path grading that stops within 10 inward blocks instead of cutting through houses.

### 2. Ritual queue parity is still partial

Current gaps:

- **Session-only active state.** `ACTIVE_RITUALS` and `CLIMATE_CHANGE_PLANS` are static maps keyed by dimension — session memory, not saved world state. Long-running rites can vanish on server crash after consuming resources. A clean-shutdown refund path exists (`RitualExecutor.cancelAllWithRefund` + `RitualEvents.onServerStopping`) but crash loss is still possible. Fix: migrate to level `SavedData`, a dimension attachment, or a ritual-anchor block entity.
- **`RitualTransaction` lacks a true rollback path.** It currently commits altar power first, then offerings, with no undo. A post-commit failure can silently lose resources. Target pattern: `validate → prepareEffect → commit → applyEffect`.
- **Representative-trigger gap.** All rite routes use one representative dropped ingredient instead of the full original multi-sacrifice recipe registry. Functionally correct but not full 1.7.10 parity.
